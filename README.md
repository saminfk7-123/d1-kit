# d1-kit

Liquid AI の判定専用モデル **d1** を使って、次の 2 つを試すためのキットです。

1. **PR のレビューの重さ**（0〜3 の 4 段階）を判定する
2. **CD が失敗したときの原因**を分類し、ログの中の原因の行を特定する

検証に使ったデータ（公開 OSS の PR と、架空の CD 失敗ログ）も一緒に入っているので、clone してキーを入れればそのまま再現できます。

> [!WARNING]
> **無料版（`d1:free`）に送った内容は、Liquid 社が保存してモデルの学習に使います。**
> 会社のコード、PR、CD のログは送らないでください。この repo に入っている検証用データだけで試してください。
> 自分の repo のデータで使う場合は、有料版（`d1`）に切り替えたうえで、Liquid の利用規約でデータの扱いを確認してください。

## d1 とは

文章を書かず、判定だけを返すモデルです。質問の形は 3 種類です。

| 型 | 返すもの | 使いどころ |
|---|---|---|
| Noul | Yes の確率（0〜1） | if 文の代わり |
| Choice | 選択肢のどれか + 各選択肢の確率 | switch 文の代わり（最大 255 個） |
| Score | 段階（2〜10 段階）+ 確信度 | 並べ替え、しきい値 |

- 入力の上限: 質問ごとに 32,768 トークン
- 料金（有料版）: 入力 100 万トークンあたり $0.04。出力は 0
- 無料版はレート制限が厳しいので、スクリプトは 1 回ごとに 3 秒空け、制限にかかったら待ってやり直します

## セットアップ

```sh
cp env.example .env
# .env の LIQUID_API_KEY を自分のキーに書き換える（console.liquid.ai の Dashboard > API Keys）
```

Python 3.10 以上があれば動きます。追加でインストールするものはありません。

## デモ画面（TypeScript）

デモを選んで実行すると、d1 に聞いた各段階の選択肢と確率、最終判定、正解との比較が表示されます。

```sh
cd demo
npm install
npm run dev          # http://localhost:5173 を開く
```

- **保存済みの結果 / ライブ実行** を右上で切り替えられます。ライブ実行の結果は `demo/cache/` に保存され、次からは保存済みとして表示できます。
- 無料版はレート制限で 1 件 10〜60 秒かかることがあります。発表などで使うときは、先に全件を実行して保存しておくと安心です。

```sh
npm run warm                 # 全 33 件をライブ実行して保存（無料版だと 20〜40 分）
npm run warm -- review aws   # 種類を絞る
npm run warm -- --missing    # まだ保存していないものだけ
```

- API キーはサーバー側（`demo/server/`）だけで読み、ブラウザには渡しません。
- 判定ロジックは Python 版と同じものを TypeScript に移したものです（`demo/server/review.ts`、`demo/server/triage.ts`）。

## 1. PR のレビューの重さ

```sh
python3 review_weight/review_weight.py                 # Express の PR 7 件で検証
python3 review_weight/review_weight.py path/to/pr.txt  # PR 1 件だけ判定（PR 本文 + git diff をテキストにしたもの）
```

### 仕組み

1. **Situation + Evaluation**（d1 を 1 回）: 変更の種類と、「動作は変わるか」「全員が使う部分か」「条件付きの変化か」「セキュリティに関わるか」「取り返しがつきにくいか」を同時に聞く
2. **Decision**（d1 を 1 回）: 1 の答えを PR に書き添えて、重さを 4 段階で判定させる
3. **ルール**: ファイルの場所で確実に分かること（例: リリース用ワークフローの変更）は、d1 に聞かずに下限を決める
4. 確信度が 0.6 未満なら「要人間」とする

| 段階 | 意味 |
|---|---|
| 0 | 誰にも影響しない |
| 1 | メンテナだけに影響する、または利用者から見た挙動が変わらない |
| 2 | 一部の利用者だけが使う部分の挙動が変わる |
| 3 | 全員が使う部分の挙動が変わる（条件付きでも）、セキュリティに関わる、取り返しがつきにくい |

### 自分の repo に合わせるには

- `review_weight.py` の先頭にある `DECISION_CRITERIA`（段階の基準）と `PATH_FLOORS`（ファイルの場所のルール）を書き換える。**基準の書き方が精度をいちばん左右します。**
- データセットのフォルダに `context.txt`（repo の影響範囲メモ）を置く。例: `review_weight/data/express/context.txt`。どのディレクトリが全員に影響するかを数行で書くだけで、判定がかなり変わります。

## 2. CD 失敗の原因

```sh
python3 cd_triage/triage.py classify snowflake     # Snowflake の短いログ 14 件で、原因の分類を検証
python3 cd_triage/triage.py classify aws           # AWS の長いログ 12 件で、原因の分類を検証
python3 cd_triage/triage.py pick-line aws          # AWS の長いログ 12 件で、原因の行の特定を検証
python3 cd_triage/triage.py log path/to/failed.log aws   # ログ 1 件を分類し、原因の行も出す
```

### 仕組み

- **classify**: ログを渡して、原因を Choice で選ばせる（認証 / 認可 / 設定値 / ビルド / 一時的、AWS 用には起動失敗 / リソースの状態も）
- **pick-line**: d1 は行番号のような自由な値を出力できないので、**コードでエラーらしい行を抜き出し、それを Choice の選択肢にする**（キーが `L213` のような行番号）。d1 が選んだキーが、そのまま原因の行番号になる

### 自分の CD に合わせるには

- `triage.py` の先頭にある `PROFILES` に、自分の CD の説明（`context`）と原因の分類（`categories`）を足す
- 分類の選択肢は、過去に実際に起きた失敗を 10〜20 件見て決めると精度が上がる
- **ログに原因が出ていないと、d1 にも分からない。** たとえば ECS のデプロイが「安定しない」で失敗したとき、ログには理由が出ない。失敗時だけ動く診断ステップ（`aws ecs describe-services`、`aws logs tail` など）を足しておくと、理由まで読める

## 検証結果（2026-10-08）

### PR のレビューの重さ（Express の PR 7 件）

| 版 | 完全一致 | 備考 |
|---|---|---|
| 1 回で判定 | 3/7 | repo の前提を知らないので、全員に影響する変更を軽く見る |
| + 影響範囲メモ | 3/7 | 全体に重めになったが、まだ足りない |
| 評価を同時に聞いてから判定 | 6/7 | 外した 1 件も「要人間」に回った |
| 評価を順番につないで判定 | 3/7 | 最初の評価の誤りが最後まで伝わった |
| 同時に聞く + 方針を基準に明記 + ルール（この repo の版） | 5/7 | 重い PR の見逃しは 0。軽い PR を 2 件重く見た |

1 件あたり: 入力 約 4,100 トークン、d1 の処理 約 0.9 秒、有料版で約 $0.00017。

### CD 失敗の原因

| データ | 原因の分類 | 原因の行の特定 |
|---|---|---|
| Snowflake の短いログ 14 件 | 14/14（紛らわしい 2 件は要人間） | ― |
| AWS の長いログ 12 件（248〜366 行） | 12/12 | 12/12 |

AWS のログ 1 件あたり: 入力 約 11,500 トークン、有料版で約 $0.0005。

### わかったこと

1. d1 は「読んで分類する」のは得意だが、「推論を何段もつなげる」のは苦手。
2. 判定の段階は、順番につなぐより、同時に並べて聞くほうがいい。順番につなぐと、最初の誤りが最後まで伝わる。
3. 確実に分かることはルールにする。d1 には曖昧な判断だけを任せる。
4. 外れの多くは d1 ではなく、基準の書き方のあいまいさが原因だった。
5. 確信度は「根拠があるか」を表さない。ログに理由がなくても、経験則で確信度 1.00 を出すことがある。

## データについて

- `review_weight/data/express/`: [expressjs/express](https://github.com/expressjs/express)（MIT License）のマージ済み PR 7 件の差分（一部を省略）。正解の段階は検証者が付けたもの
- `cd_triage/data/snowflake/`, `cd_triage/data/aws/`: **AI に作らせた架空のログ**。エラーメッセージは各ツールの実際の形式に似せているが、一字一句同じではない。アカウント ID（123456789012）やリソース名もすべて架空。AWS のログの概要は `cd_triage/data/aws/SUMMARY.md`

どのデータも件数が少なく、正解も検証者が付けたものなので、精度の数字は目安です。
